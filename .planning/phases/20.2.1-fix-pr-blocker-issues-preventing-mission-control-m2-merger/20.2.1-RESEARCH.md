
### B3: Credential Key Allowlist (commands.rs)

**Current state:** `get_credential`, `set_credential`, `delete_credential` all accept any `key: String` from WebView.

**Key discovery — where credentials are used:**
The frontend auth system uses `AuthStorage` from `@gsd/pi-coding-agent` which writes to `~/.gsd/auth.json` directly. It does NOT call the Tauri `get_credential`/`set_credential` IPC commands for auth storage.

The Tauri keychain commands were previously used in Phase 16 for OAuth PKCE verifiers. From Phase 15 implementation notes:
- `pkce_verifier_{state}` — scoped per OAuth state parameter
- These were the PRIMARY use case for keychain commands

After Phase 16, the auth layer migrated to `AuthStorage` (file-based at `~/.gsd/auth.json`). The Tauri keychain commands are now only called indirectly. Searching the TypeScript source confirms: **no current TypeScript code calls `get_credential`, `set_credential`, or `delete_credential` IPC commands** via `invoke()`.

This means the allowlist for B3 must enumerate the keys that WERE used OR that COULD be used:
- `pkce_verifier_*` pattern (PKCE verifiers — but dynamic suffix means static allowlist won't work for these)

**Recommended allowlist approach:**
The CONTEXT.md says to enumerate valid keys. Since auth migrated to `AuthStorage` and no TypeScript currently invokes these commands, the safe conservative allowlist is:
```rust
const ALLOWED_CREDENTIAL_KEYS: &[&str] = &[
    "anthropic_api_key",
    "github_token",
    "openrouter_api_key",
    "claude_access_token",
    "claude_refresh_token",
];
```
The exact set is left to Claude's discretion (per CONTEXT.md). The above covers the logical auth credential types. Exclude PKCE verifiers since those use dynamic suffixes that don't work in a static allowlist.

### B6: CORS Headers on Bun Response (server.ts)

**Empirically tested — Bun 1.3.10 headers are NOT frozen:**
```
$ bun -e "const r = Response.json({ok:true}); r.headers.set('X-Test','1'); console.log(r.headers.get('X-Test'))"
1   // ← mutable, no error
```

The current `addCorsHeaders` in server.ts (lines 289-294) mutates `response.headers` in place. This works correctly in Bun 1.3.10. The reviewer's concern was valid as a general principle but does not manifest as a bug in this version.

**However**, CONTEXT.md locks the fix to defensive reconstruction regardless:
```typescript
function addCorsHeaders(response: Response): Response {
  const headers = new Headers(response.headers);
  headers.set("Access-Control-Allow-Origin", `http://127.0.0.1:${HTTP_PORT}`);
  headers.set("Access-Control-Allow-Methods", "GET, POST, PUT, DELETE, OPTIONS");
  headers.set("Access-Control-Allow-Headers", "Content-Type, X-Window-Id");
  return new Response(response.body, { status: response.status, headers });
}
```

This pattern is safe because `new Headers(response.headers)` copies all existing headers, and `new Response(response.body, ...)` creates a fresh Response. The `response.body` is a ReadableStream that may only be consumed once — verify auth-api.ts responses don't already have a consumed body before this is called. All `handleAuthRequest` returns are `Response.json(...)` which use internal body, not a stream that's been read.

**Existing server-cors.test.ts:** The current test at `tests/server-cors.test.ts` uses `http://localhost:4000` as the expected origin (from Phase 11.1). The actual server uses `http://127.0.0.1:${HTTP_PORT}` (4200). The test must be updated to match `http://127.0.0.1:4200` when the function is updated.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Tauri updater key generation | Custom key generation | `cargo tauri signer generate` | Standard Tauri 2 tooling, produces correct Ed25519 format |
| Async sleep in Tokio | `std::thread::sleep` | `tokio::time::sleep(...).await` | Blocking thread sleep starves the executor; Tokio provides non-blocking async sleep |
| CORS header copying | Manual header string manipulation | `new Headers(response.headers)` | Headers constructor handles case-normalization, duplicates, and iteration |

**Key insight:** All fixes are targeted edits to existing code. No new modules, no new helpers, no new abstractions needed.

## Common Pitfalls

### Pitfall 1: tokio "time" Feature Missing
**What goes wrong:** Adding `.await` to `tokio::time::sleep()` without adding `"time"` to Cargo.toml features causes a compile error: `cannot find function sleep in module tokio::time`.
**How to avoid:** Change Cargo.toml `features = ["rt"]` to `features = ["rt", "time"]` first.

### Pitfall 2: server-cors.test.ts Origin Mismatch
**What goes wrong:** The existing test at `tests/server-cors.test.ts` expects `"http://localhost:4000"` (the Phase 11.1 value) but the server now uses `http://127.0.0.1:${HTTP_PORT}` (4200). The B6 fix will change `addCorsHeaders` — the test must also be updated.
**Warning signs:** `server-cors.test.ts` fails after implementing B6.

### Pitfall 3: open_external invoke in OAuthConnectFlow
**What goes wrong:** The B2 allowlist for `open_external` only permits `http://` and `https://`. But `OAuthConnectFlow.tsx` calls `invoke("open_external", { url })` with OAuth authorization URLs which are always `https://`. This is safe. Do NOT add `gsd://` or `file://` to the allowlist.
**Verification:** Check `tests/auth-phase16.test.ts` line 627: `OAuthConnectFlow openInBrowser uses Tauri invoke when __TAURI__ is in window` — confirms `open_external` is called with `authUrl` from OAuth flow, always HTTPS.

### Pitfall 4: B4 Breaks registerWindow on First Boot
**What goes wrong:** If `registerWindow` is too aggressively gated, the frontend cannot get a `wsPort` to connect to at all. The gate must only block chat message dispatch (WS `onChatMessage` handler), NOT the HTTP endpoint itself.
**How to avoid:** The `projectSelected` flag blocks only `sendMessage` calls in `onChatMessage`. The WS connection itself, state broadcasts, and `session_update` emissions should work from the start.

### Pitfall 5: Response Body Already Read
**What goes wrong:** In B6's defensive reconstruct, `new Response(response.body, ...)` passes the ReadableStream. If the body has already been consumed (e.g., by `response.json()` earlier in the handler), the reconstructed response will have an empty body.
**How to avoid:** All paths in `auth-api.ts` that return a Response use `Response.json(data)` which wraps data as the body source — the body has NOT been read by the handler before being passed to `addCorsHeaders`. The `handleAuthRequest` function returns `Response.json(...)` directly in all branches.

### Pitfall 6: Tauri Updater Pubkey Format
**What goes wrong:** The pubkey in `tauri.conf.json` must be the exact base64 string output by `cargo tauri signer generate`, with no newlines or extra whitespace.
**How to avoid:** Copy the public key from the `cargo tauri signer generate` output exactly. It looks like: `dW50cnVzdGVkIGNvbW1lbnQ6IG1pbmlzaWduIHB1YmxpYyBrZXkgRUYwRjcxQ0...`

## State of the Art

| Old Approach | Current Approach | Why It Changed |
|--------------|------------------|----------------|
| `std::thread::sleep` in async fn | `tokio::time::sleep(...).await` | Blocking sleep starves Tokio thread pool; async sleep yields |
| Mutable `response.headers.set()` | `new Response(response.body, ...)` reconstruct | Defensive against future Bun versions where Response may be frozen |
| Empty `pubkey: ""` in tauri.conf.json | Base64 Ed25519 public key | Security: empty pubkey accepts any update payload (MITM) |
| Any URL accepted by open_external | HTTP/HTTPS only allowlist | Security: prevents `javascript:`, `file://`, custom protocol exploit |
| Any key accepted by get/set_credential | Static ALLOWED_CREDENTIAL_KEYS | Security: prevents WebView from probing arbitrary keychain entries |
