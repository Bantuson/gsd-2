# Phase 20.2.7 — Security Gap Closure

## What This Phase Is

After phase 20.2.6 completed (all 4 post-audit findings resolved, 8/8 regression tests GREEN), a
structured architectural review was conducted to answer: *is there a path to a fully secure version,
or are these accepted risks permanent?*

The review produced a clear taxonomy: some risks are platform limitations, some are simple fixes that
were never done, and some are genuinely correct accepted trade-offs. This phase closes the "simple
fixes" category and applies the one architectural improvement that is tractable now.

---

## Why "Fully Secure" Is a Frame Problem

Every application has accepted risks. The correct question is proportionality: are the risks
appropriate to the actual threat model? For a localhost desktop app where the attacker is either the
user or a process already running as the user, the answer for this codebase is largely yes.

The distinction that matters:

| Category | What it means | Action |
|----------|--------------|--------|
| **Simple fix** | Gap with no architectural cost — just not done yet | Do it |
| **Platform limitation** | Requires architectural change; alternatives exist | Plan the change |
| **Genuine accepted risk** | Correct as-is; alternative would harm UX or provide no real benefit | Document it |

## In Scope

### Fix 1: Missing `require_main_window()` Guards (GAP-5, GAP-6, GAP-7)

**Severity:** Medium (GAP-7), Low (GAP-5, GAP-6)
**Effort:** Trivial — 3-line guard on 3 commands
**Files:** `packages/mission-control/src-tauri/src/commands.rs`

Phase 20.2.4 added `require_main_window()` to all credential-touching commands (B72/B31). Three
non-credential commands were missed:

| Gap | Command | Risk | Location |
|-----|---------|------|----------|
| GAP-7 | `install_update` / `check_for_updates` | Secondary window can trigger app restart or update installation | `commands.rs:152-159` |
| GAP-5 | `reveal_path` | Secondary window can open arbitrary directories in file manager | `commands.rs:169-193` |
| GAP-6 | `open_new_window` | Secondary window can spawn more windows (DoS, social engineering) | `commands.rs:263-279` |

**Fix:** Add `require_main_window(&window)?;` as the first line of each handler. Exact pattern from
the existing guard at `commands.rs:12-21`.

**Why `reveal_path` needs the guard:** If an XSS-to-IPC chain were reestablished in a secondary
window (bypassing DOMPurify), `reveal_path` with a crafted path expands the secondary-window IPC
surface beyond what B72/B31 intended.

**Why `open_new_window` needs the guard:** An attacker in a secondary window could exhaust the
`MAX_WINDOWS` cap or spawn windows for social engineering without the guard.

### Fix 2: `/api/project/switch` Path Confinement (GAP-1)

**Severity:** Medium
**Effort:** Small — one path validation addition
**File:** `packages/mission-control/src/server.ts:327-380`

The `/api/project/switch` endpoint reconfigures the server's working context to any filesystem path
supplied in the POST body. The only validation is an `access()` existence check. No confinement to
the home directory, no `..` segment normalization.

**Attack scenario (A-LOCAL):** An attacker with the launch token can switch the server to any
directory, controlling what `allowedRoot` the downstream `handleFsRequest` API uses for reads/writes.

**Fix:** Add home-directory confinement before the existence check:

```ts
import { homedir } from "os";
import { resolve, normalize } from "path";

const normalizedPath = normalize(resolve(requestedPath));
if (!normalizedPath.startsWith(normalize(homedir()))) {
  return new Response(JSON.stringify({ error: "Path must be within home directory" }), {
    status: 400,
    headers: { "Content-Type": "application/json" },
  });
}
```

**Note:** The launch token is still the primary guard (B50). This is defense-in-depth — it prevents
token-compromise scenarios from jumping to arbitrary filesystem locations.

### Fix 3: WebSocket Token — First-Message Handshake (GAP-3)

**Severity:** Low
**Effort:** Moderate — WS server + client changes
**Files:** `packages/mission-control/src/server/ws-server.ts`, frontend WS client code

The WS launch token is passed as `?token=<value>` in the URL query string. Query strings appear in:
- Browser developer tools network tab
- Any proxy logs
- Tauri WebView debug logs

**Why this is a browser spec limitation:** WebSocket upgrades cannot carry custom headers in browser
contexts — the `WebSocket` constructor does not accept headers. The current approach is the standard
workaround.

**Better alternative — first-message handshake pattern:**

1. Client connects without a token (or with a placeholder)
2. Server holds the connection in an `UNAUTHENTICATED` state — no topic subscriptions yet
3. Client sends first message: `{ "type": "auth", "token": "<launch-token>" }`
4. Server validates the token, transitions to `AUTHENTICATED`, subscribes to the appropriate topics
5. If token is invalid or absent after a 5-second timeout, server closes the connection with code 4001

```ts
// ws-server.ts — conceptual change
if (message.type === "auth") {
  if (message.token !== LAUNCH_TOKEN) {
    ws.close(4001, "Unauthorized");
    return;
  }
  ws.data.authenticated = true;
  ws.subscribe(TOPIC_PREFIX + ws.data.windowId);
  return;
}
if (!ws.data.authenticated) {
  ws.close(4001, "Unauthorized");
  return;
}
```

This eliminates the token from the URL entirely without changing the security guarantees.

## Out of Scope (Confirmed)

### B57/B71 — Plaintext auth.json (REMAINS ACCEPTED)

The architectural alternatives were evaluated:

| Alternative | Assessment |
|-------------|-----------|
| Encrypt auth.json with Tauri session key | Raises bar but same-user process can still read Tauri memory |
| Move API key storage into Tauri commands | Full rewrite of auth layer; viable long-term but not now |
| OAuth only, no API key storage | Requires provider OAuth support — not available for all keys today |

**Decision:** Keep as accepted risk. Document the long-term migration path (Tauri commands for auth)
in THREAT-MODEL.md as a future architecture item but do not implement now.

### Rate Limiter Single Global Bucket (REMAINS ACCEPTED)

All localhost traffic arrives from `127.0.0.1`. Per-client bucketing is architecturally impossible
here. The 100 req/s cap is correct and intentional.

### No TLS on Localhost (REMAINS ACCEPTED)

A self-signed cert requires the user to trust it manually, creating worse UX with no real security
benefit against a same-user attacker. Network sniffing on loopback is not a credible threat.

### `/api/fs/list` Full FS Enumeration (REMAINS ACCEPTED)

Intentional UX design — the project picker requires full FS browsing. Protected behind the launch
token (B50). Could be home-directory scoped without breaking UX, but the launch-token guard is
sufficient given the threat model.

### B23 — dep_check Warning-Only (REMAINS ACCEPTED)

The absolute-path canonicalization already prevents PATH hijack regardless of installation location.
Blocking non-standard Bun paths (nix, asdf, custom prefix) would break legitimate users for zero
security gain.

## Corrections Needed in THREAT-MODEL.md

These are documentation corrections, not code changes:

1. **B37 host allowlist:** Current text says "restricts API access to `127.0.0.1:4200` only."
   Correction: `ALLOWED_HOSTS` at `server.ts:108-109` includes both `127.0.0.1:4200` AND
   `localhost:4200`. `localhost` resolves via DNS (slightly wider surface for DNS rebinding than
   `127.0.0.1`). The text should reflect both entries.

2. **B57/B71 auth.json readers:** Current text references only `auth-api.ts` as the consumer.
   `classify-intent-api.ts:49` also reads `auth.json` directly for Haiku classification calls.
   Both read paths should be documented so a future migration doesn't miss one.

3. **Add accepted-risk entries for:** GAP-2 (FS enumeration intentional), GAP-3 (WS token in URL —
   will be resolved by Fix 3 above, so add as historical context), GAP-9 (rate limiter single
   bucket), and the `localhost:4200` DNS rebinding note.

4. **Add long-term architecture note:** Document the migration path for B57/B71 (Tauri-command-based
   auth storage) as a `## Future Architecture` section — not a commitment, just recorded intent.

## Context for Future Auditors

This codebase has been through four consecutive security phases (20.2.3 → 20.2.6). The B-matrix in
`20.2.5-CONTEXT.md` defines 64 behaviors; all are GREEN. Every "accepted risk" surfaced by external
auditors without B-matrix context has been cross-referenced and either fixed (if real) or formally
documented (if intentional). The THREAT-MODEL.md is the authoritative reference.

The remaining accepted risks are proportional to the threat model (A-LOCAL, A-NET-LOCAL). There is
no feasible path to eliminating them without degrading UX or performing a significant architectural
rewrite of the Bun/Tauri boundary — which is tracked as a future item, not a current gap.
