# Phase 20.2: GSD Playwright CLI Browser Tool Use Made Native to Mission Control — Context

**Gathered:** 2026-03-17
**Status:** Ready for planning
**Source:** User research analysis

<domain>
## Phase Boundary

Eliminate the external Chromium window that pops up when GSD uses its browser-tools Playwright extension during agent sessions. Instead, route all browser activity (screenshots, navigation, DOM snapshots) through Mission Control's existing preview panel — creating a seamless in-app browser agent experience.

The work splits cleanly into two parts:
1. **Headless mode** — suppress the external Chrome window (0.5 days)
2. **Screenshot relay** — stream browser state into the preview panel (2–3 days)

</domain>

<decisions>
## Implementation Decisions

### Core Finding
GSD's browser-tools extension (`src/resources/extensions/browser-tools/index.ts`, line 346) directly calls `chromium.launch({ headless: false })`. This single line is responsible for popping the external window. We have direct control over it.

### Approach: Two-Phase Implementation

**LOCKED: Phase 1 — Suppress the External Window**
- Add `env.GSD_BROWSER_HEADLESS = "1"` in `claude-process.ts` at line ~117 when spawning GSD from Mission Control
- Read the env var in `browser-tools/index.ts` at line 346:
  ```ts
  const headless = process.env.GSD_BROWSER_HEADLESS === "1";
  const launchOptions = { headless };
  ```
- Result: no external Chrome window; GSD still performs all Playwright work (screenshots, accessibility snapshots, DOM inspection) headlessly

**LOCKED: Phase 2 — Relay Screenshots into the Preview Panel**
- After each `browser_screenshot` or `browser_navigate`, browser-tools emits a custom NDJSON event
- `pipeline.ts` intercepts the event and broadcasts via WebSocket
- React `PreviewPanel` renders the screenshot as a live base64 image: `<img src="data:image/jpeg;base64,..." />`
- Preview panel auto-toggles between live iframe (dev server) and browser agent view (what GSD is looking at)

Data flow:
```
browser-tools (headless Chromium)
  → emits { type: "browser_state_update", screenshot, url }
  → pipeline.ts intercepts
  → ws-server publishChat()
  → React PreviewPanel renders <img src="data:image/jpeg;base64,..." />
```

### Rejected Approaches
- **CDP shared browser (connectOverCDP)** — MEDIUM feasibility, 3–4 days, defer to later/optional
- **Custom MCP wrapper** — MEDIUM feasibility, 4–5 days, only if switching to MCP architecture
- **Electron/Tauri WebView with CDP** — MEDIUM feasibility, 8–12 days, not worth it
- **iframe CDP exposure** — IMPOSSIBLE (browser security blocks this)
- **postMessage DOM bridge** — IMPOSSIBLE (cross-origin blocks this)

### Claude's Discretion
- Exact NDJSON event schema/field names for `browser_state_update` (verify in source)
- Whether to use a dedicated WebSocket message type or reuse existing publishChat channel
- Preview panel toggle UX: auto-switch vs manual button
- Screenshot quality/size (JPEG compression level for base64 relay)
- Whether to show URL bar / page title above the relayed screenshot

</decisions>

<specifics>
## Specific Implementation Details

### browser-tools/index.ts — Line 346 change
Before:
```ts
chromium.launch({ headless: false })
```
After:
```ts
const headless = process.env.GSD_BROWSER_HEADLESS === "1";
chromium.launch({ headless })
```

### claude-process.ts — Env injection (~line 117)
```ts
env.GSD_BROWSER_HEADLESS = "1";
```

### NDJSON Event (browser_state_update)
```json
{ "type": "browser_state_update", "screenshot": "<base64>", "url": "https://..." }
```

### PreviewPanel render
```tsx
<img src={`data:image/jpeg;base64,${browserState.screenshot}`} />
```

</specifics>
