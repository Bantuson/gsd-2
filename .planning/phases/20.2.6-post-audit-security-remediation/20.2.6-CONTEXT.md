# Phase 20.2.6 — Post-Audit Security Remediation

## What This Phase Is

After phase 20.2.5 completed (64/64 security behaviours GREEN), a parallel 4-auditor security review was
run against the codebase without B-matrix context. Of ~20 findings raised, cross-referencing against the
B-matrix and THREAT-MODEL.md confirmed:

- **~15** were false alarms, accepted risks, or intentional design decisions
- **1** was a better-practice improvement (not a gap)
- **3** were genuine new gaps not covered by any prior security phase

This phase closes the 3 genuine findings and applies the better-practice improvement.

---

## Why Previous Audit Findings Were Not Actionable

For PR reviewers: see `.planning/PR-SECURITY-CONTEXT.md` for the full cross-reference.
The key reason most findings were noise: auditors lacked context of the B-matrix and THREAT-MODEL.md.
Examples:
- **FE-2** ("proxy preserves upstream CSP is a vulnerability") — B39 *explicitly requires* CSP not be stripped.
  The auditor found the fixed state and raised it as a new finding.
- **FE-1** ("iframe sandbox voids itself") — B32 was "no sandbox at all." The fix added the sandbox attribute.
  The `allow-same-origin` + DOMPurify + CSP combination is the verified B25-B32 posture.
- **AUTH-4** ("plaintext auth.json") — formally accepted in THREAT-MODEL.md with full mitigation inventory.

## Genuine Findings — In Scope

### Finding 1: `kill-port.ts` Windows regex typo (FS-9)

**Severity:** Low
**Location:** `packages/mission-control/src/server/kill-port.ts:23`
**Behaviour violated:** B18 (atomic port allocation) — the kill step silently fails on Windows

**Detail:**
```ts
const parts = line.trim().split(/s+/);  // BUG: splits on literal 's+', not whitespace
//                               ^^^ should be /\s+/
```
The regex `/s+/` matches the literal character `s` followed by one or more `s` characters — it does
NOT match whitespace. On Windows, `netstat -ano` output is whitespace-delimited. All PID extractions
from the netstat output parse as `NaN` and are filtered out. The kill step silently no-ops; the app
falls back to an ephemeral port via `getEphemeralPort()`. No crash, but B18's intent (free the
specific port) is broken on Windows.

**Fix:** Change `/s+/` to `/\s+/` on line 23.

### Finding 2: `POST /api/trust` bypasses `.gsd` path validation (API-4)

**Severity:** Medium
**Location:** `packages/mission-control/src/server.ts:398-403`
**Behaviour violated:** None explicitly defined — this is a gap in the B-matrix

**Detail:**
```ts
if (pathname === "/api/trust" && req.method === "POST") {
  const body = await req.json() as { dir?: string };
  const gsdDir = body.dir ?? getPipelineForReq(req)?.getPlanningDir() ?? resolve(repoRoot, ".gsd");
  await writeTrustFlag(gsdDir);  // NO path validation, NO .gsd suffix check, NO .. normalization
  return addCorsHeaders(Response.json({ ok: true }));
}
```
`registerTrustRoutes` in `trust-api.ts` validates that `dir` ends with `/.gsd` and rejects `..`
segments, but the handler in `server.ts` calls `writeTrustFlag()` directly, bypassing those checks.
An authenticated caller (bearer token required) can supply `{ "dir": "/tmp/evil" }` and write a
trust flag file at an arbitrary path. `mkdir({ recursive: true })` creates any intermediate dirs.

**Fix:** Add `path.resolve()` normalization + `.gsd` suffix check inside the `server.ts` handler,
matching the validation in `registerTrustRoutes`. Alternatively, route the call through
`registerTrustRoutes` instead of calling `writeTrustFlag` directly.

### Finding 3: Empty `Host` header bypasses DNS rebinding guard (API-6)

**Severity:** Low
**Location:** `packages/mission-control/src/server.ts:129`
**Behaviour violated:** B37 (host header validation) — the guard does not cover the no-host case

**Detail:**
```ts
const host = req.headers.get("host");
if (host && !ALLOWED_HOSTS.has(host)) {  // null/undefined host passes through — not rejected
  return new Response(..., { status: 400 });
}
```
B37 tests validate that a *wrong* `Host` header (e.g., `evil.com`) returns 400. They do not test
the case where no `Host` header is sent at all (HTTP/1.0 clients, `curl --http1.0`, crafted local
requests). Missing `Host` evaluates to `null` → `null && ...` is falsy → the check is skipped.
Combined with FS-3 (unrestricted directory listing), a local process without a Host header can
enumerate the filesystem.

**Fix:** Change condition to `if (!host || !ALLOWED_HOSTS.has(host))` — reject missing Host too.

## Better-Practice Improvement — In Scope

### FE-5/FE-6: Use hardened `sanitizeHtml()` wrapper instead of raw `DOMPurify.sanitize()`

**Severity:** Low (not a gap — defense-in-depth improvement)
**Locations:**
- `packages/mission-control/src/components/code-explorer/CodeExplorer.tsx:346`
- `packages/mission-control/src/components/milestone/InlineReadPanel.tsx:22`

**Detail:**
Phase 20.2.5 created `packages/mission-control/src/lib/sanitize-html.ts` — a hardened DOMPurify
wrapper with an explicit `ALLOWED_TAGS` and `ALLOWED_ATTR` allowlist — to provide consistent,
restrictive sanitisation across the app. Both `CodeExplorer.tsx` and `InlineReadPanel.tsx` import
`DOMPurify` directly and call `DOMPurify.sanitize()` with no configuration, bypassing the allowlist.

The default DOMPurify config still blocks `<script>` and event handlers (the XSS-to-IPC chain is
broken), so this is not a gap in the B25-B32 posture. However, using the hardened wrapper is
strictly better: it provides an explicit allowlist rather than relying on DOMPurify defaults, which
vary by version.

**Fix:** Replace `DOMPurify.sanitize(...)` with `sanitizeHtml(...)` in both files. Remove the
direct `DOMPurify` import where it becomes unused.
