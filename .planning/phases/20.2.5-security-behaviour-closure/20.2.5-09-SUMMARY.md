## What Was Built

### Task 1: PoisonError-safe Mutex + spawn_blocking for child.wait() (bun_manager.rs)

Three sites in `bun_manager.rs` previously called `.lock().unwrap()` — if any thread panicked while holding the `BunState` mutex, all subsequent lock attempts would panic too, orphaning the Bun child process permanently.

**Fix:** All three lock sites now use:
```rust
state.child.lock().unwrap_or_else(|e| {
    eprintln!("[bun_manager] WARNING: mutex poisoned, recovering: {e}");
    e.into_inner()
})
```

**child.wait() fix:** `kill_bun_server` previously called `child.wait()` directly in an async function, which blocks the Tokio executor thread. Fixed by using `guard.take()` to move the child out and then wrapping `child.wait()` in `tokio::task::spawn_blocking`.

**Rust unit test:** Added `test_poisoned_mutex_does_not_panic` in `#[cfg(test)] mod tests` that:
1. Creates a mutex
2. Poisons it via a spawned thread panic
3. Verifies `is_poisoned()` returns true
4. Verifies the recovery pattern does NOT panic and recovers the value

### Task 2: Non-blocking folder dialog (commands.rs)

`open_folder_dialog` previously called `blocking_pick_folder()` directly in an `async fn`, blocking the Tokio executor thread during the entire time the user has the folder picker open.

**Fix:** Uses the Tauri 2.x dialog plugin's async callback variant with a tokio oneshot channel:
```rust
let (tx, rx) = tokio::sync::oneshot::channel::<Option<String>>();
app.dialog().file().pick_folder(move |folder| {
    let result = folder.map(|p| p.to_string());
    let _ = tx.send(result);
});
rx.await.unwrap_or(None)
```

This pattern: the dialog runs natively (not on the Tokio executor), the callback fires when the user selects/cancels, and the async command awaits the oneshot receiver.

**Cargo.toml:** Added `rt-multi-thread` and `sync` tokio features for `spawn_blocking` and `oneshot` support respectively.
