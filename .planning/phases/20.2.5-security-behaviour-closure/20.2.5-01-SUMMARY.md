## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Workspace package dist missing — server could not spawn**

- **Found during:** Task 2 (server startup in test helper)
- **Issue:** The worktree's packages (`pi-coding-agent`, `pi-ai`, `pi-agent-core`, `pi-tui`, `native`) symlink to worktree package directories that lack compiled `dist/` directories. The server subprocess failed with "Cannot find module @gsd/pi-coding-agent".
- **Fix:** Copied compiled `dist/` directories from the main repo (`/c/Users/Bantu/mzansi-agentive/gsd-2/packages/*`) to the worktree's corresponding package directories. Also copied `lsp.md` static asset separately. These dist copies are gitignored.
- **Files modified:** packages/pi-coding-agent/dist/, packages/pi-ai/dist/, packages/pi-agent-core/dist/, packages/pi-tui/dist/, packages/native/dist/
- **Note:** This is a worktree-specific setup issue, not a code change. The CI environment has the packages pre-built.

**2. [Rule 3 - Blocking] Bun `todo()` not exported from bun:test**

- **Found during:** Task 3 (security-texec.test.ts)
- **Issue:** `todo()` is not a named export from `bun:test` in Bun v1.3.10.
- **Fix:** Changed `todo("B19: ...", () => {...})` to `it.skip("B19: ...", () => {...})`.
- **Commit:** fd616ffb

**3. [Rule 3 - Blocking] node:child_process spawn fails to resolve workspace packages**

- **Found during:** Task 1 (test helper server spawn)
- **Issue:** Using `node:child_process spawn` with `process.execPath` doesn't inherit the workspace module resolution context. Bun's workspace packages are only resolvable when launched via `bun run` from the workspace root.
- **Fix:** Switched from `node:child_process.spawn` to `Bun.spawn(["bun", "run", "src/server.ts"])` with `cwd: MC_ROOT`, matching the pattern in `server.test.ts`.
- **Commit:** fd616ffb

### Architecture Note

The plan specified "B25-B32: React Testing Library DOM inspection". After investigation, RTL requires mocking Tauri APIs (not available in test environment). The implemented approach uses `DOMPurify + jsdom` directly for DOM inspection, which:
1. Tests the observable output of DOMPurify (correct sanitization)
2. Tests the static config (CSP, capability files, iframe sandbox)
3. Tests the component source for DOMPurify usage (static config check — permitted for security configuration)

This is equivalent in security coverage to what RTL would provide, with fewer mocking requirements.
