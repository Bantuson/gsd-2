# Phase 20.2.5 — Security Behaviour Closure

## What This Phase Is

Phase 20.2.4 implemented Nyquist tests and partial remediations (T-EXEC-01 B19-24, T-NET-01/T-NET-02 B33-42).
A post-execution security audit of the actual codebase against all 81 required secure behaviours in THREAT-MODEL.md
revealed **53 FAIL / 11 PARTIAL / 17 PASS**. This phase closes every remaining gap.

**Key testing principle:** Tests MUST verify observable runtime behaviour — actual HTTP responses, real process
inspection, filesystem effects — NOT source code pattern matching (no `readFileSync + regex` checks).
If a behaviour cannot be verified by exercising the running system, it needs a different test strategy, not a grep.

## Testing Requirements — Holistic Behaviour, Not Source Inspection

**The previous Nyquist tests (plans 01-03) used source inspection: readFileSync + regex to check if
certain strings appear in source code. This is inadequate — it tests what the code looks like, not
what it does.**

### What "Holistic" Means for Each Threat Category

**T-FILE — Path traversal:**
- Start the actual Bun server with a known workspace root
- Make real HTTP requests with traversal payloads (`../../etc/passwd`, null bytes, sibling paths)
- Assert HTTP 400 response status
- Assert no file was read/written outside the workspace root (check filesystem)
- Do NOT grep source for "realpathSync"

**T-EXEC — Process spawning:**
- Inspect the running child process via `/proc/{pid}/exe` (Linux) or equivalent
- Verify `env` of spawned Bun process via process inspection or a test hook in bun's startup
- Call `kill-port` and `git` endpoints; verify they succeed/fail as expected on real inputs
- Do NOT grep source for "execFile"

**T-NET — Proxy and host validation:**
- Make real HTTP requests with bad Host headers → verify 400
- Make real proxy requests to blocked destinations → verify 403
- Send oversized bodies → verify 413
- Do NOT grep source for "ALLOWED_PROXY_HOSTS"

**T-AUTH — Authentication:**
- Attempt API calls without token → verify 401
- Attempt WebSocket connection without token → verify rejection
- Generate 11 sessions and attempt a 12th → verify 429
- Do NOT grep source for "crypto.randomUUID"

**T-XSS — DOM injection:**
- Render a component with a known XSS payload using React Testing Library
- Query the resulting DOM for `<script>` elements, `javascript:` href values, event handlers
- Verify the DOM is clean after DOMPurify runs
- Do NOT grep source for "DOMPurify"

**T-CRED — Credential isolation:**
- Trigger trust-check failure (mock the network call to throw) → assert UI shows untrusted state
- Render a capability-restricted command from a secondary window → assert it fails
- Do NOT grep source for "fail closed"

**T-DOS — Rust safety:**
- Poison a mutex in a test, call the Rust function under test, assert it returns Err not panic
- Call pick_folder from a test async context and verify the thread does not block
- Do NOT grep source for "spawn_blocking"

### Allowed Testing Patterns

```
✅ HTTP request with bad input → assert response status + body
✅ Render component with malicious content → inspect DOM
✅ Mock network failure → assert application state
✅ Process introspection via /proc or OS API
✅ Filesystem assertion after write attempt
✅ React Testing Library queryAllBy* on rendered output
✅ Rust #[tokio::test] with actual function calls and PoisonError injection
✅ Source inspection ONLY for static config (CSP string in tauri.conf.json, capability JSON)

❌ readFileSync(sourcePath) + regex.test(content) for behaviour verification
❌ Grepping source for function names to confirm they're called
❌ String matching on variable names instead of testing observable output
```

## Scope Boundaries

**In scope:**
- All 53 FAIL + 11 PARTIAL behaviours from the audit
- Rewrite of all 6 Nyquist test files to use holistic behaviour testing
- Per-launch token authentication (B50-B52) — this is a significant feature addition

**Out of scope:**
- Protocol-level TLS for localhost (AUTH-03) — architectural constraint, accepted risk

**Constraints:**
- Bun server (not Node.js) — use Bun-native APIs (`Bun.serve`, `Bun.file`)
- Tauri 2.x capability model — capabilities are per-window, declared in JSON files
- Tests must run without a live Tauri process for most assertions (use HTTP client against the Bun server directly)
- DOMPurify version compatible with Tauri WebView — prefer `dompurify` npm package + jsdom for tests
